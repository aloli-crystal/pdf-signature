== v0.10.0 — 2026-06-05 — Backend PKCS#11 par provider (OpenSSL 3.x)

=== Ajouté

* **Backend provider `pkcs11prov`** (libp11 ≥ 0.4.12) — le successeur
  moderne de l'engine. `Pkcs11.cms_sign_provider` / `rsa_sign_provider`
  chargent la clé `pkcs11:` via l'OSSL_STORE du provider (config
  `OPENSSL_CONF` activant `pkcs11prov` + le provider `default`, module du
  token via `PKCS11_MODULE_PATH`), sans l'API engine héritée. PIN par
  variable d'environnement (jamais en argv). `Pkcs11.provider_path`
  auto-détecte le provider ; `Pkcs11.provider_available?` permet un repli.
* **`Signer.sign(pkcs11_provider: true, pkcs11_provider_path:)`** /
  `Options#pkcs11_provider?` / CLI `pdfsig sign --pkcs11-provider
  [--pkcs11-provider-path PATH]`. Fonctionne à tous les niveaux et en
  mode strict (le `signedAttrs` natif est signé par le token via le
  provider). L'engine reste le défaut.

=== Validation

Round-trip **sign → verify** via le provider avec un token **SoftHSM**
hermétique : la clé ne quitte pas le token, signature vérifiée par
`openssl cms -verify`. 60 specs, ameba 0.

== v0.9.0 — 2026-06-05 — /DSS d'archive récursif (B-LTA)

=== Ajouté

* **`DSS.add_archive_validation`** — après le DocTimeStamp d'archive,
  enrichit le `/DSS` du **certificat de la TSA d'archive** (récolté du
  jeton RFC 3161) plus d'éventuels CRL/OCSP, et ajoute un `/VRI` clé par
  le `/Contents` du DocTimeStamp. Le store existant est **fusionné** (les
  références aux flux du signataire restent valides), pas remplacé. C'est
  ce qui rend l'horodatage d'archive lui-même validable à long terme
  (ETSI EN 319 142-1, niveau LTA).
* **`Signer.sign(level: :b_lta, archive_dss: true)`** / `Options#archive_dss?`
  / CLI `pdfsig sign --archive-dss` (`-A`). **Opt-in** : ce matériel
  s'ajoutant *après* le DocTimeStamp, celui-ci ne couvre alors plus tout
  le document (un horodatage d'archive de renouvellement le scellerait) —
  un B-LTA par défaut garde un DocTimeStamp qui couvre tout.

=== Validation

B-LTA enrichi : **5 révisions incrémentales** (original + B-T + DSS +
DocTimeStamp + DSS d'archive), signature d'origine toujours valide
(`pdfsig` : « Signature is Valid »), `/DSS` final fusionné portant le
certificat de la TSA d'archive et **deux entrées `/VRI`** (signature +
DocTimeStamp). 59 specs, ameba 0.

== v0.8.0 — 2026-06-05 — PAdES strict (CMS natif, sans signing-time)

=== Ajouté

* **`PDF::Signature::CmsBuilder` — construction native du CMS.** Assemble
  un `SignedData` CAdES-BES détaché *à la main* sur le DER, avec l'ESS
  `signing-certificate-v2` mais **sans** l'attribut signé `signing-time`
  — le profil PAdES strict (ETSI EN 319 142-1 § 5.3 : le temps vient du
  `/M` et de l'horodatage, pas d'un attribut signé). `openssl cms -sign
  -cades` injecte toujours `signing-time`, d'où la construction maison.
  La bibliothèque ne fait que la structure ; la signature RSA sur le
  `signedAttrs` est produite par un bloc, donc la clé peut rester dans un
  fichier ou un HSM.
* **`ASN1`** gagne `sorted_set` (SET OF trié DER, X.690 § 11.6),
  `integer`, `octet_string`, `null`.
* **`PKCS7.sign_strict` / `PKCS7.sign_strict_pkcs11`** + `Pkcs11.rsa_sign`
  (signature du `signedAttrs` par le token). `Options#strict_pades?` et
  `Signer.sign(strict_pades: true)` ; CLI `pdfsig sign --strict` / `-s`.
  N'a d'effet qu'aux niveaux CAdES (B-T+) ; SHA-256 uniquement.

=== Validation

CMS strict **validé par deux outils tiers** : `openssl cms -verify`
(« CMS Verification successful ») et **`pdfsig` (poppler)** → « Signature
is Valid », ETSI.CAdES.detached — poppler accepte le CAdES-BES assemblé à
la main. `openssl asn1parse` confirme **0 attribut `signing-time`** et la
présence de l'ESS `signing-certificate-v2`. 58 specs, ameba 0.

== v0.7.0 — 2026-06-05 — CLI `pdfsig`

=== Ajouté

* **Binaire `pdfsig`** (target `src/cli.cr`) — l'interface en ligne de
  commande aux conventions ALOLI :
+
--
** `pdfsig sign -i ENTREE.pdf -o SORTIE.pdf -c CERT [options]` — tous
   les niveaux (b-b / b-t / b-lt / b-lta), TSA (`-t`), métadonnées
   (`-r`/`-L`/`-n`), matériel LTV répétable (`-C`/`-R`/`-O`) et backend
   PKCS#11 (`-k`/`-m`/`-P`/`-e`).
** `pdfsig verify SIGNE.pdf [-a TRUST.pem]` — un rapport par champ
   (niveau PAdES, validité, couverture). Code de sortie : 0 si tout est
   valide, 2 sinon.
** `pdfsig help [SOUS-COMMANDE]` (+ `-h`/`--help`), `pdfsig version`
   (+ `-v`/`--version`). Sous-commande inconnue refusée avec la liste
   valide.
--
* **Sécurité — aucun secret en argv.** La phrase de passe du PKCS#12 et
  le PIN PKCS#11 sont lus depuis une **variable d'environnement** dont
  on passe le *nom* (`-p`/`--passphrase-env`, `-P`/`--pkcs11-pin-env`),
  jamais la valeur — invisibles dans `ps`. Chaque flag long a un short.

=== Validation

Specs d'intégration : build du binaire puis aller-retour réel
**`sign` → `verify`** (phrase de passe via l'environnement), plus la
batterie `help` / `help <sub>` / sous-commande inconnue / arguments
manquants. 56 specs, ameba 0.

== v0.6.0 — 2026-06-04 — Backend PKCS#11 (HSM / SoftHSM)

=== Ajouté

* **`PDF::Signature::Pkcs11` — signature par clé matérielle.** La clé
  privée ne quitte jamais le module (HSM, carte à puce, SoftHSM) : elle
  est désignée par une URI PKCS#11 (RFC 7512). `Pkcs11.cms_sign` produit
  le CMS détaché via `openssl cms -sign` piloté par l'engine libp11
  `pkcs11`. L'engine et le module sont câblés par un `OPENSSL_CONF`
  jetable (0600), le PIN passe par variable d'environnement
  (`-passin env:…`), jamais en argv. `Pkcs11.engine_path` auto-détecte
  l'engine ; `Pkcs11.available?` permet un repli gracieux.
* **`Signer.sign(pkcs11_key:, pkcs11_module:, pkcs11_pin:,
  pkcs11_engine_path:)`** — bascule sur le token. `certificate` désigne
  alors le **certificat** du signataire (PEM). Le backend matériel
  fonctionne à **tous les niveaux** (B-B → B-LTA) : l'orchestration
  signature/horodatage/DSS/DocTimeStamp est unifiée (`produce_cms`) et
  indépendante du backend.
* `Options` : `pkcs11_key` / `pkcs11_module` / `pkcs11_pin` /
  `pkcs11_engine_path` (+ `pkcs11?`). B-LT récolte automatiquement le
  certificat du signataire depuis le CMS, donc le `/DSS` fonctionne
  identiquement avec une clé HSM.

=== Validation

Round-trip **sign → verify** avec un token **SoftHSM** hermétique
(`softhsm2-util` : init token, génération clé + cert, import) : B-B et
B-T signés par une clé qui **ne quitte pas le token**, signatures
vérifiées par `openssl cms -verify` et horodatage RFC 3161 embarqué
détecté. 48 specs, ameba 0. Pré-requis : `libp11` (engine OpenSSL
`pkcs11`) + un module PKCS#11.

== v0.5.0 — 2026-06-04 — Vérification

=== Ajouté

* **`PDF::Signature::Verifier` — côté lecture.** `Verifier.verify(input,
  ca_bundle)` lit un PDF signé et renvoie un `Verifier::Report` par champ
  de signature (signatures et horodatages de document), dans l'ordre du
  document. Chaque rapport expose : `field`, `kind`
  (`:signature`/`:document_timestamp`), `sub_filter`, `level`
  (`:b_b`/`:b_t`/`:b_lt`/`:b_lta`/`:document_timestamp`/`:unknown`),
  `valid?`, `covers_whole_document?`, `has_signature_timestamp?` et un
  `detail`.
* La vérification reconstruit les régions du `/ByteRange` **stocké**,
  vérifie la cryptographie via `PKCS7.verify` (signatures CMS/CAdES) ou
  `TSA.verify` (jetons RFC 3161 des DocTimeStamp), et **infère le niveau
  PAdES** atteint à partir du SubFilter, de la présence d'un horodatage
  de signature, d'un `/DSS` et d'un horodatage de document. Avec
  `ca_bundle`, les chaînes signataire / TSA sont validées contre cet
  ancrage de confiance ; sans lui, seules les mathématiques de signature
  le sont.

=== Validation

Round-trip **sign → verify** sur les quatre niveaux : B-B
(`covers_whole_document? == true`, pas d'horodatage), B-T (horodatage
détecté), B-LTA (deux rapports : la signature `:b_lta` ne couvre pas tout
le document, le DocTimeStamp `:document_timestamp` le couvre). Avec un
bundle de confiance combiné (CA émettrice + CA de la TSA), signature et
horodatage d'archive ressortent tous deux `valid?`. 44 specs, ameba 0.

== v0.4.0 — 2026-06-04 — PAdES B-LTA (horodatage d'archive)

=== Ajouté

* **`PDF::Signature::DocTimeStamp` — horodatage de document (ISO 32000-2
  § 12.8.5).** `DocTimeStamp.add` ajoute un dict `/Type /DocTimeStamp`
  `/SubFilter /ETSI.RFC3161` dont le `/Contents` est un **jeton RFC 3161
  brut** (pas un CMS) couvrant **tout le document** — signature et `/DSS`
  compris. Posé via un nouvel incremental update : un champ de signature
  supplémentaire (`/V` → DocTimeStamp) ajouté à l'`/AcroForm /Fields` et
  aux `/Annots` de la page. Le `/ByteRange` couvre tout sauf le trou
  `/Contents` du jeton.
* **`Signer.sign(level: :b_lta, …)`** — produit une signature B-LT puis
  scelle l'ensemble par un horodatage d'archive. Tous les niveaux PAdES
  baseline (B-B → B-T → B-LT → B-LTA) sont désormais disponibles.
* **`ByteRange.compute(bytes, contents_size, from:)`** — paramètre `from`
  pour viser le `/Contents` du DocTimeStamp (le document contient
  désormais plusieurs trous `/Contents` de même taille).

=== Validation

PDF B-LTA **validé par `pdfsig` (poppler)** : deux signatures détectées
— la signature CAdES (« Signature is Valid ») et le **DocTimeStamp**
(`Timestamp1`) dont les *Signed Ranges* couvrent **tout le document**
(« Total document signed »). Le jeton d'archive est par ailleurs vérifié
par `openssl ts -verify` (contre la CA de la TSA) sur les octets du
`/ByteRange`. Specs hermétiques (PKI locale + TSA RFC 3161 locale),
4 révisions incrémentales. 40 specs, ameba 0.

=== Limitations connues

* L'enrichissement *récursif* du `/DSS` avec le matériel de validation
  propre à la TSA d'archive (pour re-valider l'horodatage lui-même à très
  long terme) n'est pas encore automatisé — le jeton embarque toutefois
  le certificat de la TSA (option `-cert`), donc il reste auto-portant.

== v0.3.0 — 2026-06-04 — PAdES B-LT (/DSS, matériel de validation)

=== Ajouté

* **`PDF::Signature::DSS` — Document Security Store (ISO 32000-2
  § 12.8.4.3).** `DSS.add` embarque le matériel de validation
  long-terme — chaîne de certificats (`/Certs`), CRL (`/CRLs`) et
  réponses OCSP (`/OCSPs`), chacun en flux indirect — plus une entrée
  `/VRI` clé par le **SHA-1 (hex majuscule) du DER de la signature**.
  Tout est ajouté par un **second incremental update**, après le
  `%%EOF` de la signature : le `/ByteRange` s'arrête là, donc le DSS
  tombe hors signature et celle-ci reste valide.
* **`PDF::Signature::Incremental`** — briques d'incremental update
  (objets, table xref, trailer `/Prev`) extraites de `Signer` et
  partagées avec `DSS`.
* **`Signer.sign(level: :b_lt, …)`** — produit une signature B-T puis
  ajoute le DSS. Le certificat **signataire** (depuis le CMS) et les
  certificats de la **TSA** (depuis le jeton d'horodatage) sont récoltés
  automatiquement ; la CA émettrice, les CRL et OCSP arrivent par les
  options `ltv_certs` / `ltv_crls` / `ltv_ocsps` (chemins PEM ou DER).
  `PKCS7.certificates` extrait les certificats embarqués d'un CMS ;
  `DSS.load_der` lit du PEM ou du DER ; `DSS.signature_der` relit le DER
  de la signature.

=== Validation

PDF B-LT **validé par `pdfsig` (poppler)** → « Signature is Valid » avec
« Not total document signed » (comportement *attendu* : le DSS est un
ajout post-signature légitime, hors `/ByteRange`). La signature reste
vérifiable par `openssl cms -verify` après l'ajout du DSS, et le `/DSS`
est relu par le parser. Les specs montent une **PKI hermétique**
(CA locale émettrice + réponse OCSP générée hors-ligne + CRL) en plus de
la TSA RFC 3161 locale — aucun service réseau. 39 specs, ameba 0.

== v0.2.0 — 2026-06-04 — PAdES B-T (horodatage RFC 3161)

=== Ajouté

* **`PDF::Signature::ASN1` — lecteur/écrivain d'arbre DER minimal.** Juste
  assez d'ASN.1 (forme à tag court, longueur définie, ré-encodage
  canonique) pour faire la chirurgie qu'exige B-T : analyser le CMS
  détaché produit par `openssl cms`, localiser le `SignerInfo`, lire sa
  valeur de signature et y greffer un attribut non-signé. Ré-encodage
  octet-pour-octet d'un nœud inchangé (DER canonique) — la branche
  signée n'est jamais perturbée. Fondation réutilisée par la v0.4 (/DSS)
  et la v0.5 (vérification).
* **`PDF::Signature::TSA` — client RFC 3161.** Construit le `TimeStampReq`,
  le POST en HTTP (`application/timestamp-query`), récupère le
  `TimeStampToken` et le vérifie — via `openssl ts` (même choix de
  shell-out CLI que `PKCS7`), seul le transport HTTP étant en Crystal.
  Authentification HTTP Basic optionnelle.
* **`PKCS7.sign_with_timestamp`** — signe (CAdES-BES, cf. ci-dessous)
  puis horodate : le jeton RFC 3161 est calculé sur la valeur de
  signature du `SignerInfo` (ETSI EN 319 122 § 5.2.3) et greffé comme
  attribut non-signé `id-aa-timeStampToken` (1.2.840.113549.1.9.16.2.14).
  Ajouts utilitaires : `signature_value`, `embed_timestamp_token`,
  `timestamp_token` (relecture du jeton embarqué).
* **CAdES-BES via `openssl cms -sign -cades`.** Le chemin CAdES ajoute
  l'attribut signé ESS `signing-certificate-v2` (RFC 5035), exigé par le
  SubFilter `ETSI.CAdES.detached`. Sans lui, un validateur CAdES
  (`pdfsig` de poppler) rejette la signature.
* `Options` accepte `tsa_url`, `tsa_digest_algorithm`,
  `tsa_username`/`tsa_password` ; `Signer.sign(level: :b_t, tsa_url: …)`
  produit une signature B-T. B-T sans `tsa_url` lève une `SignatureError`.

=== Validation

PDF B-T **validé par trois outils tiers** : `openssl cms -verify`
(signature CAdES), `openssl ts -verify` (jeton RFC 3161 contre la CA de
la TSA) et **`pdfsig` (poppler)** → « Signature Validation: Signature is
Valid », type ETSI.CAdES.detached, « Total document signed ». Les specs
montent une **TSA RFC 3161 locale et hermétique** (serveur HTTP en
process adossé à `openssl ts -reply`) : l'échange complet est joué hors
ligne contre un vrai `openssl` des deux côtés.

=== Limitations connues

* `openssl cms -cades` inclut l'attribut signé `signing-time`, que le
  profil PAdES (ETSI EN 319 142-1 § 5.3) recommande d'omettre au profit
  du `/M` et de l'horodatage. Écart mineur — la signature reste un
  CAdES-BES valide. La construction native du CMS (qui permettrait de
  l'omettre) est laissée à un palier ultérieur.

== v0.1.3 — 2026-06-04 — PAdES B-B fonctionnel

=== Ajouté

* **`Signer.sign_with_options` — orchestration PAdES B-B complète.** Le
  PDF d'entrée est signé par un **incremental update** : les octets
  d'origine restent intacts et l'on ajoute, en fin de fichier, le dict
  /Sig (placeholders /Contents + /ByteRange), le champ de signature
  (widget /FT /Sig invisible), l'AcroForm (/SigFlags 3), les versions
  mises à jour de la page (/Annots) et du catalog (/AcroForm), une table
  xref incrémentale et un trailer /Prev. Le /ByteRange réel et le
  /Contents (PKCS#7 hex) sont ensuite patchés in-place.
* `ByteRange.compute` distingue le /Contents **hexadécimal de la
  signature** du /Contents de la page (référence vers le flux).
* Placeholder /ByteRange élargi à 4 entiers de 10 chiffres pour un patch
  in-place sans décalage.

=== Validation

PDF signé **validé par deux outils tiers** : `openssl cms -verify`
(round-trip dans les specs) et **`pdfsig` (poppler)** sur un vrai
fichier → « Signature Validation: Signature is Valid », « Total document
signed », type adbe.pkcs7.detached, SHA-256.

=== Changé

* Dépendance `pdf` relevée de `~> 0.5` à `~> 1.0` (1.6.0) pour AcroForm /
  champ de signature et writer xref-stream.

== v0.1.2 — 2026-06-04

=== Ajouté

* **`PKCS7.sign` / `PKCS7.verify`** — le cœur cryptographique de PAdES
  B-B, implémenté via la CLI `openssl` (le choix de conception du
  `doc/RATIONALE.adoc`). `sign` extrait le certificat feuille et la clé
  privée du PKCS#12 (passphrase passée par variable d'environnement,
  jamais sur la ligne de commande ; matériel PEM dans un répertoire
  temporaire 0700 supprimé en `ensure`) et produit un CMS SignedData
  **détaché** (`openssl cms -sign -binary -outform DER -nosmimecap
  -md <digest>`). `verify` valide une signature détachée contre un
  contenu fourni, éventuellement contre un bundle de CA.
* Specs : un aller-retour (sign puis verify) avec un PKCS#12 auto-signé
  généré à la volée, une vérification du caractère détaché (le contenu
  signé n'est pas embarqué dans le DER), le rejet d'une altération, et
  l'erreur PKCS#12 introuvable. La mécanique de signature (insertion
  `/Sig`, `/ByteRange`, patch `/Contents`) arrive dans la prochaine
  0.1.x.

== v0.1.1 — 2026-05-07

=== Fixed

* **`PDF::Signature::VERSION` lue au compile-time depuis `shard.yml`**
  (au lieu d'être hardcodée). Pattern reproduit identiquement dans
  `aloli-crystal/pdf` v0.5.4 et `aloli-crystal/crystal-combine-pdf`

  Crystal et le `version:` du `shard.yml` peuvent diverger silencieusement
  parce que le bump manuel de release oublie l'un ou l'autre. Avec le
  macro `read_file` ce risque disparaît.

* Spec `pdf_signature_spec.cr` adapté : compare `PDF::Signature::VERSION`
  au `version:` parsé de `shard.yml` à l'exécution.
